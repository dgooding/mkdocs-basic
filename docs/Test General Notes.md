# Test General Notes

This document is a practical reference for writing and maintaining ITSD documentation. It is intentionally classified as **Other** so the library also demonstrates how useful content can exist outside the main SOP, technical, training, and reference categories.

## What a good page answers

Before publishing, check that a reader can identify:

- Who the guidance is for.
- What outcome it supports.
- When it applies and when it does not.
- What prerequisites, permissions, or approvals are required.
- Which steps are safe to perform and when to stop.
- Who owns the next action if the procedure fails.

## Writing standards

Use a direct title, short paragraphs, descriptive headings, numbered steps for ordered work, and tables for comparable values. Define abbreviations the first time they appear. Use example values only when they are clearly marked as examples. Never place passwords, tokens, private keys, personal data, or production-only connection details in documentation.

## Review checklist

- [ ] The owner and intended audience are clear.
- [ ] The content has a review date and a change reference.
- [ ] Links work and point to authoritative sources.
- [ ] Steps have been tested in the appropriate environment.
- [ ] Security, privacy, access, and rollback considerations are included.
- [ ] Screenshots and examples do not expose sensitive data.
- [ ] Search terms match the words people use in tickets.
- [ ] Outdated or duplicate guidance has been removed or linked clearly.

## Suggested metadata

```text
Owner: ITSD Service Operations
Audience: Service desk analysts
Status: Draft | Approved | Retired
Review date: YYYY-MM-DD
Change reference: CHG-0000 or DOC-0000
```

Metadata is useful only when the team agrees where it belongs and who maintains it. Keep it consistent across related pages.

## Publishing principle

Documentation is part of the operational control, not an afterthought. Update the page when the process changes, ask a colleague to test unclear steps, and use the support channel to report gaps. A short, accurate page is more valuable than a comprehensive page nobody can trust.
